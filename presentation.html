01 The problem

Today, it all lives in a spreadsheet.

  • 1Anyone can edit anything. No roles, no rules: a client could "accept" their own request.
  • 2No history. Who moved a request to "delivered", and when? Nobody knows.
  • 3Messy exports. Duplicates, blank values, mixed date formats, unknown robots.
  • 4Double booking. The same video can end up in two clients' datasets.
  • 5No numbers. How fast do we deliver? Which robot is busiest?

02 Who uses it

Three roles, checked on the server.

🏢

Client

Creates requests ("200 episodes of pick cup by 20 Oct"), sees only their own, reviews each delivered episode, chats with their operator.

🛠️

Operator

Sees every request, moves it through the workflow, imports episodes, filters and assigns them, chats on the requests they work on.

🛡️

Admin

Everything an operator can do, plus creates and deactivates users and changes roles. Reads every chat.

Rule

Hiding a button is not security. Every endpoint checks the token (401) and the role (403). Another client's request answers 404: we don't even admit it exists.

The difference between 401 and 403: 401 means "I don't know who you are", 403 means "I know you, but you may not". The 404 for another client's data is deliberate.
03 The workflow

A request's life, one rule table.

Invalid move → 409 · wrong role → 403

Every change is saved with who and when, in the same transaction

The UI's buttons come from the server (allowed_next)

The whole state machine is 10 lines in workflow.py. The frontend never re-implements it: the API tells each user which moves they may make, and the page draws those buttons.
04 What I built

Three containers, one command.

Migrations

Alembic: the same tables on every machine, versioned.

Auth

bcrypt passwords, JWT tokens, role guards on every endpoint.

Logging

One JSON line per request: method, path, status, time, user.

/health

Checks the database too; answers 503 when it is down.

On every start the API runs the migrations, creates the seed users, imports the seed CSV, then starts. That is why one command is enough from a clean clone.

06 Rules that cannot be broken

Two layers: clear messages, and the database.

  • ✓One episode, one request: UNIQUE(episode_id) on assignments.
  • ✓Only good or usable episodes can be assigned, all-or-nothing per batch.
  • ✓Deliver needs at least the requested number of episodes.
  • ✓Row lock (SELECT … FOR UPDATE) while a request changes.
  • ✓CHECK constraints on role, status, quality.
# two operators, one episode, same instant — 8 rounds

round 8:  200  409
# never a double assignment, never a 500

I removed my own pre-check on purpose: the database still refused. Only the "nice message" test failed.

If two people click at the same second, application checks can both pass. The UNIQUE constraint is the final guard, and its error is turned into the same clean 409.

Keeping 2 Returning 1 Rejecting 1
  • KKeep: accepted and locked. The operator can't remove it later.
  • RReturn: more than I asked for. Freed for other clients.
  • ✕Reject (with a reason): back to rework; it stops counting.
  • !Asked for 2, got 5? A plain accept is refused: return the extras or extend the request (logged in the chat).
A request is like a contract. Silently accepting 5 when 2 were asked would hand over more than agreed and block episodes another client needs. The server enforces this, the UI only guides.

In SQL, not Python

GROUP BY, percentile_cont(0.5) for the median. The number of queries doesn't grow with the data (tested).

At 5 million episodes

A month stays fast (indexes read only the range). A full year ≈ 8 s → next step: a daily roll-up table.

One index, measured

(quality, recorded_at) INCLUDE (task_name): 17 ms → 5.6 ms.

Why the median and not the average? One request that took three weeks would drag the average up; the median is the typical request. The 12-month query reads almost the whole table, which is why a roll-up table is the first fix at scale.

11 Something that went wrong

1 test in 40 failed. Not my code.

  1. 1Symptom: random 401 on a token issued a millisecond earlier.
  2. 2Reproduce: a loop test, 250 logins, print the token's iat next to the clock.
  3. 3Cause: Docker's virtual machine clock jumped ~22 s. The token looked "issued in the future".
  4. 4Fix: accept 60 s of clock difference + a test for it.
# what the loop printed on failure
now          = 1790776076.86
token iat    = 1790776099      ← 22 s ahead
error        = ImmatureSignatureError

# security.py
jwt.decode(token, secret,
           algorithms=["HS256"],
           leeway=60)
What I learned: when a test is flaky, don't retry it until it passes. Make it fail on demand, print what the code sees, then fix the cause. Clocks between machines are never equal.
12 Security

What's in, and what I'd worry about.

In place

  • 🔒 bcrypt passwords, same error for wrong email or password
  • 🎫 JWT with a fixed algorithm (unsigned tokens refused)
  • ⚡ Deactivation works at once, not at token expiry
  • 🧾 Pydantic validation + CHECK constraints
  • 📦 25 MB upload limit, UTF-8 only, bound SQL parameters
Worry 1

Broken access control

A client changing /requests/7 to /8. Every endpoint checks on the server, with tests per role.

Worry 2

Token theft through XSS

The token is in localStorage. Next: an httpOnly cookie, a Content-Security-Policy, login rate limiting.

I'm honest about the gaps: localStorage is simple but readable by any script on the page, and there is no rate limiting yet.
